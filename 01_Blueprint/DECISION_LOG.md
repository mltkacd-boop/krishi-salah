# Project Decision Log
## Safe Pesticide Use Knowledge and Advisory Assistant for Decision Support

This log records every approved architecture/scope decision in chronological order. It is updated whenever architecture or implementation changes, per the master prompt's documentation rule (Section 7). Each entry states **what was decided, why, and what it changes in the architecture.**

---

### DEC-001 — Overall Architecture Approved
- **Date:** Phase 1 review
- **Decision:** The Phase 1 blueprint's overall architecture is approved, including the **Rule-Based Safety Engine having veto authority** between retrieval and LLM generation (i.e., the LLM can never render a recommendation that the rule engine has not approved).
- **Rationale:** This is the core safety guarantee for Objective 2 — ensures the LLM never originates agricultural fact.
- **Architecture impact:** None (confirms Phase 1 design as-is). All subsequent modules (B–F) must preserve this gating order: Classify → Retrieve → Rule-Check → (Approve → Advisory) OR (Block → Escalate).

### DEC-002 — Geographic Scope: India
- **Decision:** The project targets **India**, using Indian agricultural regulations and **CIB&RC-registered pesticide products** only. Every product approval and permitted use entered into the knowledge base must be verified against authoritative sources before inclusion.
- **Rationale:** Matches the team's realistic data-access capability (publicly available Indian government/extension sources) and keeps the regulatory scope coherent — mixing geographies would make "approved use" ambiguous.
- **Architecture impact:**
  - `sources.geography` field (already in schema) becomes a **mandatory, enforced** field, not optional metadata — Phase 3 ingestion must reject any source without a confirmed India/CIB&RC-applicable geography tag.
  - Source research (Phase 3) is scoped to: CIB&RC label database, State Agriculture Department bulletins, ICAR/KVK advisories.

### DEC-003 — Multilingual Pilot: English + Hindi
- **Decision:** The multilingual pilot supports **English and Hindi**. The architecture must allow additional Indian languages to be added later without redesign.
- **Rationale:** Hindi is the most broadly usable second language for the target user base (advisors/farmers) and for team validation capability. Extensibility avoids rework when adding more languages post-pilot.
- **Architecture impact:**
  - All language-dependent artifacts — i18next string bundles, `kb_chunks.language`, `query_log.language`, and the fixed escalation-template dictionary (Section 14) — are **keyed by ISO language code**, not hardcoded to two values.
  - No change needed to classifier/RAG/rule-engine logic itself; only to data/string resources when a language is added later.

### DEC-004 — LLM Provider: Ollama (local), Provider-Agnostic Interface
- **Decision:** Use **Ollama with a locally hosted model** as the initial/default LLM provider to minimize API cost. The AI Advisory Module (F) must access the LLM through a **provider-agnostic interface**, so a cloud LLM API can be integrated later without redesigning the system.
- **Rationale:** Removes a paid-API dependency for the academic deliverable; local inference is free and sufficient for the "paraphrase approved evidence" role (the LLM is never the fact source, so a smaller local model is acceptable).
- **Architecture impact:**
  - Introduces an explicit `LLMProvider` interface (e.g., `generate(prompt, language) -> text`) in Module F.
  - `OllamaProvider` is the only concrete implementation built in Phase 2/7. A future `CloudAPIProvider` can be added as a second implementation without touching Modules B–E or the prompt-construction logic.
  - Adds a new risk to track: local inference latency/quality on team hardware (tracked in Phase 2 plan risk table).

### DEC-005 — Pilot Crops and Knowledge Base Target

The verified-record count takes priority over hitting a fixed number — **no fabricated products, approvals, dosages, or permitted uses** are allowed to pad the count.

### DEC-010 — Phase 3.1 Safety-and-Provenance Audit: Gating, Per-Product Safety, Schema Hardening
- **Date:** Phase 3.1 execution
- **Decision:**
  1. **(F1 — missing PHI/REI/PPE) Educational-vs-actionable gating, not a Phase 4 block.** All 9 pilot records lack any published PHI/REI/PPE value (confirmed again by this audit — see below). This gap does **not** block Phase 4 (Supervised Classification), which only needs crop/pest labels and is independent of safety-field completeness. Instead, a new computed field `ApprovedUse.advisory_status` (`ACTIONABLE_WITH_EVIDENCE` | `EDUCATIONAL_ONLY`) is added to `models.py` so every current and future consumer (API, frontend, a later RAG/rule module) automatically treats a record with any unpublished safety field as retrievable for education but never presentable as an actionable dose recommendation. A dedicated authoritative safety-data acquisition pass (seeking PHI/REI/PPE-publishing sources, e.g. CIB&RC product labels) remains an explicitly tracked open task, required before Phase 6 (Rule-Based Safety Engine) can approve any record as `ACTIONABLE_WITH_EVIDENCE` in practice.
  2. **(F2 — per-product safety data) Optional per-intervention `safety_restrictions`.** PHI/REI legally attach to a specific registered product+label, not to an entire pest-management record that may list several interchangeable chemical options with different restrictions. `Intervention.safety_restrictions: Optional[SafetyRestrictions]` is added to `models.py`. It defaults to `None` and is **never auto-copied** from the existing record-level `ApprovedUse.safety_restrictions`, which is retained unchanged for backward compatibility. `advisory_status` checks the intervention-level value when present, falling back to the record-level value otherwise.
  3. **(F7 — misleading completeness wording) Corrected.** Five intervention `description` fields in `approved_uses.json` previously implied a kept chemical-option subset was "exactly as the source groups them." Each was rewritten with the actual source option count and an explicit "subset, not the complete list" (or "includes all N, not a subset") statement, verified against a fresh live re-fetch of each source.
  4. **(F8 — schema validation gaps) Closed at the schema level, not just by a dataset test.** `ApprovedUse.interventions` now requires `min_length=1` (an empty list was previously accepted). `Source` gained a `model_validator` rejecting a record with `publication_date=None` and no `publication_date_note` (previously only caught by a test, not by construction). The dead/no-op `SafetyField._value_required_if_published` field_validator (asserted nothing) was removed; the real PUBLISHED/NOT_PUBLISHED_IN_SOURCE rule has only ever lived in `SafetyRestrictions.model_post_init` and continues to.
  5. **Provenance manifest.** `knowledge_base/seed_data/provenance_manifest.json` (new) records, for each of the 9 approved_use records: the source URL, retrieval date (2026-11-03), fetch method, a SHA-256 of the fetched document, byte count, a verbatim excerpt, a MATCH/MISMATCH verdict, and human notes. All 9 live re-fetches — including the 3 sources Phase 3 had not yet re-verified (cotton pink bollworm, maize fall armyworm, the wheat PDF) — returned `MATCH`: every dosage/value transcribed into `approved_uses.json` is confirmed present verbatim in the cited source as of this audit. **Explicit distinction preserved:** a SHA-256 hash in this manifest proves *integrity* (the hashed bytes are the ones quoted) — it does **not** prove *authenticity* (that the bytes were not tampered with in transit) or *regulatory approval* (that CIB&RC has certified the quoted product/dose). See `provenance.py`'s module docstring and `ApprovedUse.verification_note` for the project's only actual claim: *source verification*, never regulatory approval.
- **Rationale:** Matches the user's explicit F1/F2 resolution: audit now without blocking independent Phase 4 work; keep incomplete records available for retrieval while structurally preventing them from being rendered as safe actionable advice; add per-product safety capacity without fabricating or auto-copying values; hold the line that this project has never claimed and must never silently start claiming CIB&RC regulatory approval.
- **Architecture impact:**
  - `backend/app/knowledge_base/models.py`: `Source` model_validator added; dead `SafetyField` validator removed; `ApprovedUse.interventions` now `Field(min_length=1)`; new `Intervention.safety_restrictions: Optional[SafetyRestrictions]`; new `ApprovedUse.advisory_status` computed_field.
  - `backend/app/knowledge_base/provenance.py` (new): `ProvenanceRecord`, `ProvenanceManifestError`, `load_provenance_manifest()` — a static, pre-computed JSON loader (no network call at application load, preserving Phase 3's DB-independence design); re-running the live audit remains a manual/CI step.
  - `backend/app/knowledge_base/__init__.py`: exports extended with the above new symbols.
  - `knowledge_base/seed_data/approved_uses.json`: 5 intervention descriptions corrected (F7); no dosage/value changed.
  - `knowledge_base/seed_data/provenance_manifest.json` (new): 9 audit entries.
  - `backend/tests/test_provenance_audit.py` (new, 21 tests): manifest coverage/shape, F7 wording removed, F8 schema rejections, `advisory_status` gating logic (default/override/non-chemical cases), per-intervention backward compatibility.
  - `frontend/src/types/api.ts`: `Intervention.safety_restrictions` and `ApprovedUse.advisory_status` added to stay in sync with the backend schema.
  - `frontend/src/pages/KnowledgeBase.tsx`: the previously hardcoded "Verified source recommendation" badge replaced with an honest `advisory_status`-driven badge ("Actionable, with evidence" vs "Educational only — safety data incomplete"), plus a page-level note distinguishing source verification from regulatory approval.
  - No existing endpoint route, response shape (beyond the additive fields above), or working feature was removed or rewritten; `/knowledge-base/*` API changes are purely additive since `advisory_status`/`safety_restrictions` are already part of the Pydantic response models.
- **Known gap (not an architecture change, a data-coverage gap, unchanged from DEC-009):** 0 of 9 pilot records have any PUBLISHED PHI/REI/PPE field; every pilot record therefore currently computes `advisory_status == "EDUCATIONAL_ONLY"`. This is the honest current state, not a bug — closing it requires the dedicated safety-data acquisition pass noted above, scheduled before Phase 6.

### DEC-011 — Phase 4 Supervised Classification: Separate Heads per Label Space
- **Date:** Phase 4 execution
- **Decision:**
  1. **Three independent classifier heads over one shared TF-IDF feature space**, rather than one joint label or a `MultiOutputClassifier`. Crop (7 labels), task (6 labels) and safety topic (8 labels) are logically independent — "mandi price of rice" is `crop=rice` + `task=out_of_scope` — so a joint 7×6×8 = 336-way label would have under one example per class with 211 rows and could not represent "unrecognised crop, clear safety question". A `MultiOutputClassifier` hides the per-target class sets, thresholds and confidences, and the clarification logic needs per-dimension confidence to ask *which* dimension is unclear. The vectorizer is fitted once on training text only (unsupervised, so no label leakage) and shared across the three heads.
  2. **Classifier:** TF-IDF (word unigrams + `char_wb` 3–5 grams, `sublinear_tf`) with `LogisticRegression(C=10, solver="liblinear", class_weight="balanced")` per head. Selected on training-split 5-fold CV (mean accuracy 0.756) and, among statistically tied options, on development-split probability spread (mean max-probability 0.649; 0/87 dimensions saturated above 0.95) — because a confidence gate is meaningless if every query is ~1.0 confident. `class_weight="balanced"` because the label mix is genuinely skewed (101 vs 10 rows) and under-predicting rare safety topics is the wrong failure for a safety tool.
  3. **Abstention over guessing.** Per-dimension `min_confidence = 0.40` and `min_margin = 0.15`, set a priori (not tuned on the test split). A dimension failing either gate is reported as `ambiguous` and the API returns `requires_clarification` plus a ready-to-show question in the detected language. Added a documented vagueness guard (no crop + general guidance + generic safety + ≤4 tokens) because confidence alone cannot catch "Is it safe?" — too few words for the wrong reading to look unlikely.
  4. **Explicit non-answer labels.** `unsupported_crop`, `no_crop` and `out_of_scope` exist so out-of-scope input is recognised and refused instead of being coerced into a pilot crop. Verified by test: no out-of-scope crop is ever *confidently* labelled a pilot crop.
  5. **Non-approval is a typed part of the response**, not a doc note: `SafetyPolicy.approves_pesticide_recommendation: Literal[False]` and `can_override_educational_only_gate: Literal[False]` on every response. The classification package imports nothing from `app.knowledge_base`, so it structurally cannot lift the Phase 3.1 `EDUCATIONAL_ONLY` gate.
  6. **Dataset:** 211 hand-labelled queries (English 125, Devanagari Hindi 60, romanised Hindi 26) in `ml/classification/dataset/queries.csv`, generated by a deterministic authoring script that rejects duplicates. No row is copied from the Phase 3 knowledge base (training corpus and retrieval corpus stay disjoint) and no row asserts a dose, PHI, REI, PPE value or registration status — products appear only as the subject of a question, so the dataset cannot inject an invented pesticide fact.
  7. **Leakage control:** a deterministic greedy 3-way allocation (seed 42) balancing all three label spaces, followed by assertions that no normalised query text spans two splits and that every label appears in every split. Single-column `stratify=` was rejected after it left `out_of_scope` and `rei` entirely absent from the test split — an evaluation that silently never tests a class.
- **Rationale:** Implements Objective 2's classification stage with real supervised learning (no LLM substitution), keeps the module runnable without PostgreSQL or Ollama, and makes the uncertainty path the default rather than an afterthought: on held-out data every confident crop prediction was correct (17/17), while misses were absorbed as clarification requests.
- **Architecture impact:** New `backend/app/classification/` package (labels, preprocessing, model, service, schemas) and `backend/app/api/classification.py` (`POST /classification/classify`, `GET /classification/model-info`), registered additively in `main.py` — no existing route changed. New training/evaluation tooling under `ml/classification/` plus a committed joblib artifact inside the backend package. Frontend `AdvisoryAssistant` screen replaced its placeholder with a plain-language interpretation panel. 83 new backend tests (132 total).
- **Two Devanagari defects found and fixed (relevant to Phase 5 RAG):** (a) `[^\w\s]` filtering destroyed Hindi because `\w` excludes combining marks (`धान` → `ध न`); (b) scikit-learn's default `token_pattern` `\b\w\w+\b` cannot match a Devanagari word at all, so Hindi was invisible to word-level features and only char n-grams saw it. Fixing (b) moved crop test accuracy 0.78 → 0.84. Phase 5 chunking/tokenisation must not repeat either mistake.
- **Known gaps (measured, disclosed in `docs/PHASE4_CLASSIFICATION_REPORT.md` §12):** 211 rows is small — held-out test has 32 rows and per-class support 1–11, so per-class metrics are directional only. Task macro F1 is 0.49 because `pest_identification` (0/3) collapses into `pest_management` and `out_of_scope` (0/2, the smallest class) is rarely recognised; joint "all three correct" is therefore 50%. Hindi coverage (61 rows) is thinner than English, and one of five Hindi crop probes abstains. Probabilities are not formally calibrated. Abstention is high at 28%, deliberately on the safe side. Unsupported-crop recall is 1/3 explicit, with the other 2 falling back to clarification (safe, less specific). Single annotator, no agreement statistic. Retraining remains a manual/CI step.

### DEC-012 — Phase 5: PostgreSQL + pgvector Integration, Scope of the Safety Gate in SQL

- **Date:** Phase 5 execution
- **Decision:** The knowledge base gains a real PostgreSQL implementation behind the existing `KnowledgeBaseRepository` interface, with the JSON repository retained as the default and as the documented fallback. Seven sub-decisions follow.

  1. **A separate, project-local database cluster instead of the existing installation.** The machine's PostgreSQL 18 runs with `scram-sha-256` for every `pg_hba.conf` entry and no administrator password was ever recorded, so the application cannot authenticate to it (measured: `psql -U postgres -h 127.0.0.1 -w` → `fe_sendauth: no password supplied`). Phase 5 forbids guessing that password and forbids enabling `trust` authentication. `scripts/setup_database.py --init-local-cluster` therefore runs `initdb` into `.pgdata/` (git-ignored) on port **55432**, bound to `127.0.0.1` only, with `scram-sha-256` for host and local connections and a randomly generated superuser password. The existing installation is neither read, modified, nor weakened. No Windows service is registered: start/stop are explicit.
  2. **A least-privilege application role.** `pesticide_app` is created `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION`, owns only `pesticide_advisory`, and `PUBLIC` is revoked from that database. The superuser credential is written only to `.pgdata/admin-credentials.json` (0600, git-ignored) because `CREATE EXTENSION` requires superuser; it is never in source, `.env`, or a log.
  3. **The safety gate is implemented twice on purpose — in Python and in SQL.** `approved_use_advisory_status` is a **view**, not a stored column, so it cannot go stale, and `PostgresKnowledgeBaseRepository.assert_advisory_status_consistency()` proves the view and the Pydantic `advisory_status` rule agree for every record. The importer fails if they disagree. Two independent implementations are the point: a single one would be a single point of failure for the project's core safety claim.
  4. **The anti-fabrication rules are re-enforced as database `CHECK` constraints**, not only in Pydantic: a `PUBLISHED` safety field must carry a value, `NOT_PUBLISHED_IN_SOURCE` must carry an explanatory note, `verification_status` is closed to the two honest values (no `APPROVED`/`REGISTERED`), and a missing `publication_date` must carry a note. A hand-written `INSERT` cannot bypass them. Tests assert the database *rejects* each violation.
  5. **Vector storage does not hard-require pgvector.** Measured blocker: the pgvector *server* extension is absent from this PostgreSQL 18 installation (no `share/extension/vector.control`, no `lib/vector.dll`) and cannot be compiled here (no C toolchain; `cl.exe`/`nmake` absent). Migration 0003 therefore stores vectors in a plain `real[]` column and *opportunistically* upgrades to pgvector: when the extension exists it builds an HNSW (or ivfflat) index on `(embedding::vector(384))` and searches with `<=>`; otherwise it uses an exact `cosine_similarity()` scan. `vector_storage_mode` records which path the database actually got, so the application reports `array` today rather than claiming pgvector. Migration 0001 was likewise changed from a bare `CREATE EXTENSION` (which aborted the whole chain) to an attempt whose outcome is recorded.
  6. **The embedding provider is a deterministic lexical hasher, and is described as such.** `HashingEmbeddingProvider` (feature hashing over words, bigrams and character 3–5-grams, L2-normalised, 384-dim) runs offline, needs no download, and is reproducible, so retrieval tests assert exact behaviour. It is **not** semantic: it has no synonymy or cross-lingual ability, and absolute cosine scores are low (≈0.15–0.35) even for correct matches — ranking, not thresholding, is the valid use. `SentenceTransformerProvider` exists behind `EMBEDDING_PROVIDER` for a real model, and `embedding_model` is stored per row so a mixed-provider index is detectable.
  7. **Every retrieved chunk carries the safety gate.** Search results join `approved_use_advisory_status`, and `RetrievedChunk.is_actionable` is true only for `ACTIONABLE_WITH_EVIDENCE`. `POST /knowledge-base/similar` therefore cannot return a source-transcribed dosage without also returning `advisory_status: EDUCATIONAL_ONLY` and `is_actionable: false`. Retrieval remains retrieval: it recommends nothing, and Phase 6/7 still own answer composition.

- **Rationale:** Phase 5's completion criteria require a working connection, working pgvector, imported records and green tests — but two of those are blocked by the environment, not by the code. The choices above keep every safety property intact while making the phase genuinely runnable: the database connects, all 9 records and 43 interventions import, 60 chunks are indexed and searchable, and the gap (pgvector) is recorded in a table, reported by `/health/pgvector` and by `/knowledge-base/status`, and documented rather than papered over. Refusing to ship anything until the extension could be installed would have left the phase untestable; shipping a `CREATE EXTENSION` that fails would have been dishonest.
- **Architecture impact:**
  - New: `backend/migrations/0002_knowledge_base_schema.sql`, `0003_vector_storage.sql`; `backend/app/knowledge_base/postgres_repository.py`, `factory.py`; `backend/app/vector/` (`embedding.py`, `chunking.py`, `store.py`); `backend/app/db/import_knowledge_base.py`; `backend/app/api/retrieval.py`; `backend/app/schemas/retrieval.py`; `scripts/setup_database.py`; `scripts/audit_secrets.py`; `backend/tests/test_phase5_postgres.py`.
  - Changed: `0001_enable_pgvector.sql` (non-fatal), `app/db/connection.py` (bounded pool, `dispose_engine`), `app/db/run_migrations.py` (raw DBAPI cursor), `app/main.py` (retrieval router, additive), `app/knowledge_base/__init__.py` (factory export), `backend/.env.example`, `.gitignore`.
  - Backend selection is a single environment variable, `KB_REPOSITORY` (`json` default, `postgres`, `auto`). Existing consumers import the same six-method interface unchanged. `POST /classification/classify`, `/knowledge-base/crops|sources|approved-uses`, and the health endpoints are unchanged and re-tested.
  - **Known gaps:** pgvector unverified on this machine (blocker reported with exact evidence and three options); pgvector code path (`<=>` + HNSW index) is written and exercised only when the extension is present, so it is unproven here; the lexical embedder has no semantic generalisation; the project-local cluster does not auto-start on boot; single-node, single-user, no replication or backup policy — this is a development database, not a deployment.

- **Review addendum (Phase 5 review, after initial implementation):** Phase 5 was accepted as *substantially implemented* but **not approved as complete**. Four corrections were made during the review, and one claim was retracted:
  1. **Retracted claim.** "pgvector works" was never supported and must not be stated. Measured position: the extension is absent (`pg_available_extensions` has no `vector` row), `CREATE EXTENSION vector` has never succeeded, `vector_storage_mode.mode = 'array'`, and the `<=>`/HNSW branch has never executed. The three-way distinction (array path implemented+tested+executed; extension not installed; pgvector code written but unexecuted) is now documented in `docs/PHASE5_VECTOR_CAPABILITY_STATUS.md`. Acceptance requires the five checks in its §4.4.
  2. **Secret scanner defects fixed.** The allow-list skipped any line containing `#`, `example`, `test_` or `assert`, which could hide a real secret; it is narrowed to runtime secret acquisition only. The `(?i)` flag had also been dropped when the leading `\b` became a lookbehind, so `DB_PASSWORD=…` no longer matched. The scanner now has both positive controls (8 samples, including a secret in a comment and in a test fixture) and negative controls (the two real local credentials must appear in zero committable files).
  3. **A committed credential was found and removed.** `02_Phase2_Setup/PHASE2_IMPLEMENTATION_PLAN.md` contained a hardcoded development value assigned to `POSTGRES_PASSWORD` on two lines (the value is not reproduced here, since quoting it would recreate the finding); both are now shell indirection that fails if unset. No live credential matched it (Docker is not installed), but it violated the project's own rule and would fail a CI gate.
  4. **Documentation accuracy.** The report's `.gitignore` appendix is now generated from the file (98 lines, round-trip verified) instead of transcribed, because the earlier copy carried a stale line count.
  - **Unchanged:** the working local PostgreSQL implementation was not deleted; no code path in the array-based vector store was altered; Phase 6 has not been started.

### DEC-013 — Phase 6: Extractive Grounded RAG, with the Decision Gate Ahead of the Text

- **Date:** Phase 6 execution
- **Decision:** The RAG pipeline composes answers **extractively** from knowledge-base fields and never calls a generative model. `generation_mode: "extractive"` is part of the response contract. Five consequences follow.
  1. **Non-invention is structural, not prompted.** Every sentence of agricultural content is assembled from a field that was transcribed from a named source. There is no model that could produce a dose, PHI, REI or PPE value, so "never invent pesticide approvals or safety values" does not depend on a system prompt holding. The trade-off is acknowledged: wording is mechanical and there is no paraphrase or follow-up conversation.
  2. **Similarity does not decide whether to answer — the Phase 4 classifier plus crop agreement does.** This is measured, not assumed: with the lexical embedder the in-scope Hindi query `धान का तना छेदक` scores 0.111 while the out-of-scope `what is the mandi price of rice today` scores 0.311. A similarity threshold would therefore answer the wrong question and decline the right one. Similarity is used only for ranking and for the reported confidence.
  3. **Pest identity is matched by rare-token alignment, and crop words are excluded from it.** Within one crop several records tie on crop boost, and raw similarity ranked "Spotted bollworm / Spiny bollworm" first for a pink-bollworm query. Document-frequency weighting fixes that ("pink" distinguishes; "borer" does not). Conversely, letting crop words count made `bacterial blight in rice` align with the insect record "Rice Leaf Folder" — a disease question answered with a pesticide record. Both cases are now fixed and asserted in tests.
  4. **Hindi is answered at crop level rather than guessed.** The embedder has no cross-lingual ability, so a Devanagari pest name cannot match English record names. The pipeline lists the records that exist for the detected crop, labelled as such, with citations and low confidence (`answer_scope: "crop"`). Retrieved chunks are not trusted for this: a Devanagari cotton query scored highest against *maize* and *tomato* chunks, so crop-scope records come from the knowledge base, not from retrieval.
  5. **Unsupported evidence produces a closed-enum refusal, never a partial answer.** `outcome` is one of seven values; `answer` is null for six of them. Unmatched pest → `insufficient_evidence`; unpublished PHI/REI/PPE → `safety_value_not_published`; any approval question → `no_regulatory_verification`. `usage_policy` and `advisory_status: EDUCATIONAL_ONLY` travel with the answer so a caller cannot render the text without the gate. The decision is made before composition, which is what makes it impossible to write a confident paragraph for a question that should be declined.
- **Rationale:** Ollama remains forbidden by the project owner, so "grounded generation" had to be satisfied without a local LLM. Extractive assembly meets the requirement — grounded, cited, refuse-when-unsupported — while making the safety property checkable by construction. The recorded costs: no paraphrasing, no multi-turn dialogue, and answers that read as structured extracts.
- **Architecture impact:**
  - New: `backend/app/rag/` (`schemas.py`, `evidence.py`, `generation.py`, `pipeline.py`, `__init__.py`), `backend/app/api/rag.py`, `backend/tests/test_phase6_rag.py`.
  - Changed: `app/main.py` (additive `rag.router`), `app/rag/*` only. Existing routes, repositories and the Phase 4 classifier are untouched; `POST /classification/classify` and the knowledge-base endpoints are re-tested.
  - Provenance: citations carry `provenance_sha256` from the PostgreSQL `provenance_records` table, falling back to the Phase 3.1 audit manifest when the JSON repository is active (otherwise every JSON-backed citation would silently lose its digest).
  - Retrieval now drops chunks that cannot be attributed — orphan chunks and records whose source is missing — because an uncitable chunk can only be answered from without a citation.
  - **Known gaps:** answers are English/Hindi scaffolding around English source values (crop names are localised; quoted source notes stay in the source language and are labelled as quotations); no semantic or cross-lingual retrieval, so a Hindi query retrieves poorly and falls back to crop level; no LLM, so no paraphrase or follow-up dialogue; pgvector still unverified, so vector search runs on the exact `real[]` scan.

### DEC-014 — Phase 7: A Deterministic Safety Gate, and Why "Actionable" Is Currently Unreachable

- **Date:** Phase 7 execution
- **Decision:** Safety decisions are computed by five deterministic rules (blueprint §12) before any text is composed. No model, no sampling, no wall clock outside an injected `ctx.today`. Four consequences:
  1. **Actionability is now gated by three independent requirements, not one.** A record must publish PHI, REI and PPE for *every* chemical intervention, **and** carry a recorded CIB&RC registration check, **and** have been traced to a fetched source page. The second requirement is new in Phase 7 and it is unsatisfiable with the current data: `verification_status = VERIFIED_SOURCE_RECOMMENDATION` means, by the model's own docstring, "not cross-checked against the live CIB&RC registry", and no registry check has ever been run. So **no record can currently be served as an actionable recommendation**, and that is the correct outcome, not a defect. `ACTIONABLE_RECOMMENDATION` remains reachable — `RuleContext.regulatory_verification` records a completed check — and a test proves both branches. A rule that can never pass would be a constant wearing a rule's name.
  2. **The recommendation gate is a field, not a hardcoded `False`.** `regulatory_verification: Mapping[record_id, bool]` defaults to empty; absence is treated as *unverified*, never as approved. When a verified registry source exists, the gate opens without touching rule logic.
  3. **Two axes are kept apart.** `actionability` answers "may this be acted on?" (two values, mirrors `ApprovedUse.advisory_status` and the Phase 5 SQL view). `decision` answers "what kind of answer is this?" (six values: actionable, educational, safety refusal, regulatory verification required, escalation, clarification). Collapsing them is what would let an incomplete-safety record render as an actionable dose; keeping them separate is what lets the engine explain *why*.
  4. **The Phase 6 contract is extended, not changed.** `decision` and `missing_information` are new optional response fields; `outcome`, `answer`, `citations`, `advisory_status` and every existing refusal behave exactly as before (the Phase 6 suite passes unchanged). Queries refused at the Phase 6 gate never reach the rules, so their decision class is mapped from the gate outcome rather than left null — with `rule_trace.evaluated = false` still saying plainly that no rule ran.
- **Rationale:** the project's recurring failure mode is a confident paragraph built from real data that does not support it. A deterministic gate that can only restrict, never generate, is the cheapest way to make that impossible; the cost is verbosity and a hard-coded refusal whenever a field is absent. Contradictions between sources block rather than resolve, and the conflicting numbers are deliberately withheld from the finding text — quoting "7 vs 21 days" inside a refusal would hand over the value the refusal exists to withhold.
- **Architecture impact:**
  - New: `backend/app/rules/` (`context.py`, `rules.py`, `engine.py`, `escalation.py`, `schemas.py`), `backend/app/api/rules.py` (`POST /rules/evaluate`, `GET /rules/status`), `backend/app/schemas/rules.py`, `backend/tests/test_phase7_rules.py`, `backend/tests/test_phase7_matrix.py`.
  - Changed additively: `app/main.py` (rules router), `app/rag/schemas.py` (`decision`, `missing_information`), `app/rag/pipeline.py` (runs the engine on selected records; maps gate refusals to decision classes). No Phase 5 migration, no schema change to `ApprovedUse`, no change to Phase 6 outcomes.
  - **Known gaps:** `ACTIONABLE_RECOMMENDATION` is unreachable until a CIB&RC verification source exists; the freshness window (5 years) is a policy choice, not a measured fact, and five of eight sources publish no date at all; contradiction detection compares only leading numbers of PHI/REI and only between records with identical normalised pest names, so a differently-worded pest name hides a conflict; the Hindi classifier does not recognise Hindi regulatory questions, so those are answered educationally (never as approved) rather than refused.

- **Security audit addendum (before Phase 8):** the regulatory gate originally accepted `Mapping[record_id, bool]`, i.e. any caller — including a future endpoint or a test fixture promoted to production — could open it with `{record_id: True}`. A truthy value is not evidence. Corrected as follows:
  1. **Evidence is a validated object, not a flag.** `app/rules/verification.py` defines `RegulatoryEvidence` (record id, registry fixed to CIBRC, printed registry reference, date the check was performed, evidence URL, SHA-256 of the evidence document, who performed it). It is frozen with `extra="forbid"`, so it cannot be edited or extended after validation.
  2. **`is_verified()` is the boundary.** It type-checks for `RegulatoryEvidence`, re-checks the *inner* record id against the requested one (evidence cannot be re-keyed to cover another record), rejects a non-CIBRC registry, a blank reference, and a future-dated check. Booleans, strings, dicts shaped like evidence and lists all fail closed. The date is re-validated inside `is_verified` because `model_copy(update=...)` bypasses Pydantic and can produce an instance carrying a string — a real bypass found while writing the audit tests.
  3. **Evidence can only come from a backend file.** `load_regulatory_evidence()` reads `knowledge_base/seed_data/regulatory_verification.json` (git-tracked, absent today → nothing verified). A malformed or duplicated manifest raises `RegulatoryEvidenceError` instead of degrading to "partially verified"; the pipeline treats any loader failure as *no* evidence, so the failure direction is closed. `answer_query` deliberately takes no evidence argument.
  4. **The HTTP surface cannot name it.** `RagRequest` and `RuleEvaluateRequest` both set `extra="forbid"`; 17 candidate field names and the query-string form are tested to return 422 / no change. `advisory_status` is a computed field and the knowledge-base routes are GET-only (write verbs return 405).
  5. **Behaviour is unchanged where it matters.** Production was and remains closed (no manifest exists, so no record is actionable); the change removes an internal forgery path rather than altering any served outcome. Phase 6 responses, outcomes and citations are untouched; `regulatory_evidence_source` and `regulatory_evidence_records` were added to the rule trace so an audit can see whether evidence was present.
  - **Residual risk, stated rather than hidden:** `answer_query(store=..., bundle=...)` and `RuleEngine(rules=...)` remain Python-level seams for tests. They are not reachable over HTTP, and a fabricated bundle would still have to satisfy `is_verified` against the backend manifest, which is empty. Cryptographic authenticity is not claimed: the evidence manifest records that a human performed a check and where, not that the registry signed it.
